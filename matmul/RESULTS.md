# matmul 结果记录

> **硬件与软件**：机器 B，HP OMEN 17 笔记本，RTX 3080 Ti Laptop GPU（Ampere，sm_86，58 SM，4 MB L2），CUDA 12.4，Nsight Compute（`--clock-control none`）。
> 笔记本 GPU 的时钟随负载变化：重负载时约 1.4 GHz，对应 FP32 峰值约 21 TFLOPS；标称 31.2 TFLOPS 对应 2.1 GHz。
> 所以不同运行之间直接比毫秒不完全可靠，**主要看"相对 cuBLAS 的百分比"**。
>
> **⚠ 测量方法修正（第 11 课之后）**：这台笔记本连续满载几十毫秒后会突然降频。旧的测试框架是**顺序计时**（先测完 cuBLAS 再测自己的 kernel），
> 后测的一方会落在降频之后吃亏，所以下面各课里 **2048³ 的"相对 cuBLAS"百分比都偏低**（1024³ 一轮只有十几毫秒，基本不受影响）。
> 框架已改为 **cuBLAS 与 kernel 交替计时**，修正后的数字见文末「测量方法修正：交替计时」一节。旧表保留原样，作为当时的记录。

|---|---|---|---|---|
| cuBLAS SGEMM | 参照 | 0.195 ms | 11.0 | 100% |
| v1 naive，x→行（反面教材） | 一个线程算一个输出；相邻线程算相邻的**行** | 13.9 ms | 0.15 | 1.4% |
| v1 naive，x→列，块 8×32 | 相邻线程算相邻的列，但一个 warp 跨 4 行 | 2.13 ms | 1.01 | 9.1% |
| v1 naive，x→列，块 32×8 | 相邻线程算相邻的**列**（合并访存） | 1.71 ms | 1.26 | 11.5% |
| v2 共享内存分块（TILE=32） | block 合作把 A、B 小块搬进共享内存，再在片上复用 | 1.43 ms | 1.50 | 13.6% |
| v2 共享内存分块（TILE=16） | 同上，block 改小为 16×16，每 SM 可驻留 6 个 block | 1.32 ms | 1.63 | 14.9% |
| v3 一维寄存器分块（TN=8） | 每个线程算同一行 8 个输出，A 读进寄存器复用 8 次 | 1.14 ms | 1.88 | 17.2% |
| **v4 二维寄存器分块（8×8）** | 每个线程算 8×8 个输出：8 个 A × 8 个 B 外积 | **0.535 ms** | **4.02** | **36.8%** |
| v5 双缓冲（预取） | 算这一块时把下一块读进寄存器，两份共享内存轮换 | 0.507 ms | 4.24 | 38.4% |
| v6 float4 显存读 + A 转置存放 | 每线程每步 1 条 float4 读 A、1 条读 B；A 转置后每个 kk 的 8 个数连续 | 0.367 ms | 5.86 | 53.6%（2048³：60.6%） |
| **v7 线程→输出改为相隔 64 的两组** | 每个线程的 8×8 拆成 2×2 组 4×4，相邻线程读写相邻地址 | **0.335 ms** | **6.42** | **58.7%**（2048³：**69.8%**） |
| **v8 warp 级分块（warp 64×32）** | block→warp→线程三级分块；寄存器降到 128，每 SM 放 2 个 block | **0.278 ms** | **7.74** | **70.1%**（2048³：**72.2%**） |

## 第 1–2 课：naive 与合并访存

**做法**：保持计算不变，只改"线程 → 输出元素"的映射和线程块形状，用 Nsight Compute 量 L1 的访存模式。

| 指标（ncu） | x→列 32×8 | x→列 8×32 | x→行 32×8 |
|---|---|---|---|
| 全局读 request 数 | 67.1M | 67.1M | 67.1M |
| 每个 request 的 sector 数 | 2.5 | 2.5 | 16.5 |
| 每个 request 碰到的 cache line 数（手算） | 1 | 2.5 | 16.5 |
| L1 命中率 | 87.5% | 87.7% | 98.0% |
| DRAM 吞吐（占峰值） | 10.6% | 6.8% | 2.7% |
| L1/TEX 吞吐（占峰值） | 98.4% | 97.6% | 97.9% |

**结论**
- **合并访存**：x→行时一个 warp 的 32 个线程读 A 的 32 个不同行，每次读要碰 32 个 sector；x→列时是 1 个。实测 sector 总数相差 6.6 倍，与手算的 33 : 5 一致，时间相差约 8 倍。
- **复用体现在命中率，不体现在 sector 数**：87.5% = 1/8 miss。A 的一个 sector 供同一 warp 的连续 8 次 k 循环使用；B 的一个 sector 被同一 block 的 8 个 warp 共用。
- **sector 数相同，cache line 数也要看**：8×32 的块和 32×8 的 sector 数一样，但读 A 时一次碰 4 条不同的 line，慢了约 25%。按数据反推，这两种慢的配置都接近"每 SM 每周期处理约 1 条 line"（待用 ncu 指标直接验证）。
- **瓶颈**：不是 DRAM（约 10%），也不是算力（FFMA 只占指令的 21%，约用到 FMA 峰值的 6%）；是 **L1/TEX 被读请求占满**。每做 1 条 FFMA 就要 2 条全局读，这是下一课 tiling 要解决的问题。

## 第 3 课：共享内存分块（v2，TILE = 32）

**做法**：一个 32×32 的 block 负责 C 的一个 32×32 小块；沿 K 每步由每个线程搬 1 个 A、1 个 B 进共享内存，`__syncthreads()` 后在共享内存里做 32 次乘加，再同步。

| 指标（ncu，1024³） | v1（x→列 32×8） | v2 |
|---|---|---|
| 时间 | 1.71 ms | 1.43 ms |
| 全局读 request | 67.1M | **2.1M**（少 32 倍 = TILE） |
| 每条 FFMA 配的全局读 | 2 | **0.0625** |
| 每条 FFMA 配的共享内存读 | 0 | **1.25**（源码是 2；编译器把 As 一行连续 4 个数合成一条 128 位读） |
| 共享内存 bank 冲突 | — | 0 |
| L1 命中率 / L2 命中率 | 87.5% / 87.4% | 0% / 70.9%（复用已搬进共享内存；不同 block 读同一小块靠 L2） |
| L1/TEX 吞吐 | 98.4% | 79.9% |
| 活跃 warp（占用率） | 96.7% | 66.6%（1024 线程的 block，每 SM 只放得下 1 个） |

**结论**
- 全局读按预期减少到 1/TILE，但时间只快了约 1.2 倍。
- 原因：共享内存读也走 SM 里同一个 L1/TEX 单元。每条 FFMA 仍要配 1.25 条共享内存读，访存指令只从 2 条/FFMA 降到约 1.3 条/FFMA；再加上每步两次全 block 同步、每 SM 只有 1 个 block，同步时没有别的 block 填空档（后两点待用 stall reason 验证）。
- 下一步（寄存器分块）：让每个线程算多个输出，把读进寄存器的数复用多次，降低"共享内存读 / FFMA"。

### TILE = 32 vs 16（block 大小与占用率的取舍）

| 指标（ncu，1024³） | TILE=32 | TILE=16 |
|---|---|---|
| 时间 | 1.43 ms | **1.32 ms** |
| 每 SM 驻留 block / 活跃 warp | 1 / 66.6% | 6 / 96.8% |
| 全局读 request / 每条 FFMA 配的全局读 | 2.1M / 0.0625 | 4.2M / 0.125（= 2/TILE，翻倍） |
| 每条 FFMA 配的共享内存读 | 1.25 | 1.25（与 TILE 无关） |
| L1/TEX 吞吐 | 79.9% | **95.7%** |

- 小 block 让每个 SM 同时有 6 个 block，一个 block 在屏障上等时其他 block 继续跑，占用率从 67% 升到 97%，时间快约 8%。
- 代价是全局读翻倍，但它在访存指令里占比很小（总共约 1.31 → 1.375 条/FFMA）。
- L1/TEX 吞吐已到 96%：**这个设计的天花板就是"每条 FFMA 约 1.3 条访存指令"**，再调 block 大小也没用，下一步必须降低共享内存读 / FFMA。

## 第 4 课：一维寄存器分块（v3，BM=BN=64，BK=8，TN=8，512 线程）

| 指标（ncu，1024³） | v2（TILE=16） | v3 |
|---|---|---|
| 时间 | 1.32 ms | **1.14 ms** |
| 每条 FFMA 配的全局读 | 0.125 | **0.031**（= 2 / (BK·TN)） |
| 每条 FFMA 配的共享内存读 | 1.25 | **0.281**（源码 72/64；编译器把连续 4 个数合成 128 位读 → 18/64） |
| FFMA 占全部指令 | 27% | **68%** |
| 共享内存 wavefront / bank 冲突 | 50.4M / 0 | 69.2M / **33.6M** |
| L1/TEX 吞吐 | 95.7% | 80.3% |
| 活跃 warp | 96.8% | 60.1% |
| 写 C 每个 request 的 sector | 4 | 32（每个线程写 8 个连续数，但同一条指令里线程间隔 32 B） |

**结论**
- 共享内存读 / FFMA 从 1.25 降到 0.28（4.4 倍），FFMA 在指令中的占比从 27% 升到 68%；但时间只快约 13%。
- **新出现的 bank 冲突**：读 `Bs[kk][tx*8 .. +3]` 时，线程 tx 和 tx+4 的地址相差 32 个 float，落在同一组 bank 上，形成 2 路冲突。按"128 位读每次处理 8 个线程"的模型算，每个 warp 每步 132 个 wavefront、64 个冲突，和 ncu 数字吻合（推断）。
- 占用率降到 60%（512 线程的 block，推测受寄存器数限制，待 `-Xptxas -v` 确认）。

## 第 5 课：二维寄存器分块（v4，BM=BN=128，BK=8，TM=TN=8，256 线程）

| 指标（ncu，1024³） | v3 | v4 |
|---|---|---|
| 时间 | 1.14 ms | **0.535 ms**（快 2.1 倍） |
| 每条 FFMA 配的全局读 | 0.031 | **0.016**（= 8 / (BK·TM·TN)） |
| 每条 FFMA 配的共享内存读 | 0.281 | **0.0625**（每步 32 条 128 位读：As 每行 8 个连续 k 合成 2 条 × 8 行，Bs 每个 kk 2 条 × 8） |
| FFMA 占全部指令 | 68% | **81%** |
| 每个线程寄存器 | — | **158** |
| 活跃 warp（占用率） | 60% | **16.6%**（158 寄存器 × 256 线程，每 SM 只放得下 1 个 block = 8 个 warp） |
| L1/TEX / SM / DRAM 吞吐 | 80% / 25% / 5% | **30% / 24% / 6%** |
| 共享内存 bank 冲突 | 33.6M | 4.2M |

**结论**
- 共享内存读 / FFMA 降到 0.06，访存不再是瓶颈：L1/TEX 只有 30%。
- **占用率只有 16.6%，却快了 2 倍**：每个线程每个 kk 有 64 条互不依赖的 FFMA，同一个 warp 自己就能连续发射（指令级并行，ILP），不需要很多 warp 轮流来隐藏延迟。
- 现在没有任何单元满载（L1/TEX 30%、SM 24%、DRAM 6%）→ 瓶颈变成**延迟**：每步"搬 → 同步 → 算 → 同步"串行执行，搬运时计算单元空等，而每个 SM 只有 8 个 warp，补不上空档（推断，待用 stall reason 验证）。

### v4 的瓶颈分析：warp 在等什么（ncu，1024³）

grid 只有 8×8 = 64 个 block，每个 SM 一次只放得下 1 个 → 第一轮 58 个、第二轮只剩 6 个，52 个 SM 空等（尾部效应 / wave quantization，有效利用约 64 / (2×58) = 55%）。
换成 2048³（256 个 block，约 4.4 轮）后，相对 cuBLAS 从约 40% 升到 **50.9%**（2.648 ms vs cuBLAS 1.349 ms），与预测一致。

`Warp Cycles Per Issued Instruction` = 4.72：每个调度器只有 2 个 warp，平均每周期只发出约 0.42 条指令。按原因分解（每发射一条指令平均等待的周期）：

| 原因 | 值 | 含义 |
|---|---|---|
| selected | 1.00 | 发射本身（基线） |
| **long_scoreboard** | **0.90** | 等显存读回来（把读到的值写进共享内存时卡住） |
| not_selected | 0.64 | 另一个 warp 被选中（不算真正的等待） |
| short_scoreboard | 0.54 | 等共享内存读回来 |
| lg_throttle | 0.40 | 全局读指令排队（每个线程每步连发 8 条） |
| dispatch_stall | 0.40 | 分派阻塞 |
| barrier | 0.26 | 等 `__syncthreads()` |
| wait / mio_throttle / math_pipe_throttle | 0.23 / 0.18 / 0.05 | 固定延迟 / 共享内存通道排队 / 计算单元忙 |

**结论**：最大的真实等待是显存读（long_scoreboard + lg_throttle ≈ 1.3），算力几乎不忙（math_pipe_throttle 0.05）。
"搬"和"算"没有重叠，是下一步（双缓冲 / 预取）要解决的问题。

## 第 6 课：双缓冲 / 预取（v5）

| 指标（1024³） | v4 | v5 |
|---|---|---|
| 时间（1024³ / 2048³） | 约 0.50 ms / 2.648 ms | 0.507 ms / 2.627 ms（基本不变；2048³ 为 cuBLAS 的 51.3%） |
| 每个线程寄存器 | 158 | 128 |
| 活跃 warp | 16.6% | 18.7%（58 个 SM 先各放 1 个 block，剩下 6 个 block 放到 6 个 SM 上：(52×8 + 6×16)/58 ≈ 8.8 个 warp / 48 ≈ 18.4%） |
| 共享内存读 / FFMA | 0.0625 | **0.156**（每步 80 条：As 不再被合并成 128 位读，每个 kk 单独读 8 次） |
| bank 冲突 | 4.2M | 8.4M |
| 等待：long_scoreboard（等显存） | 0.90 | **0.05** |
| 等待：mio_throttle（共享内存通道排队） | 0.18 | **0.90** |

**结论**
- 预取确实消除了"等显存"（0.90 → 0.05），但时间没有变快：瓶颈换成了共享内存通道排队。
- 原因是编译器这次少用了寄存器（128），不再把 As 一整行提前读进寄存器，而是每个 kk 逐个读 As 的一列 → 共享内存读指令多了 2.5 倍。
- 教训：改一处代码可能改变编译器的寄存器分配和指令选择，**必须重新测量，不能只按原理推断**。
- 下一步：把 As 转置存进共享内存，让每个 kk 需要的 8 个 A 在共享内存里连续，不依赖编译器也能用 128 位读取。

## 第 7 课：float4 显存读 + A 转置存进共享内存（v6，在 v5 基础上）

| 指标（1024³） | v5 | v6 第一次（显存仍逐个读） | v6 |
|---|---|---|---|
| 时间 | 0.507 ms | 0.457 ms | **0.367 ms**（2048³：2.225 ms，cuBLAS 的 60.6%） |
| 显存读请求 | 524,288 | 524,288 | **131,072**（每 warp 每步 2 条 × 65,536 个 warp 步） |
| 每个请求的 sector / sector 总数 | 4 / 2.09M | 16 / 8.39M | 16 / **2.09M** |
| 共享内存读（每步每 warp） | 80 | 32 | 32（As 64 → 16 条 128 位读，Bs 本来就是 16） |
| 共享内存读 / FFMA | 0.156 | 0.0625 | 0.0625 |
| 寄存器 | 128 | 127 | 127 |

**结论**
- A 转置后，每个 kk 需要的 8 个 A 在共享内存里连续，用 2 条 128 位读取出，不再依赖编译器 → 共享内存读回到 0.0625。
- 显存读如果写成 `v.x = p[0]; v.y = p[1]; ...`，编译器不确定 16 字节对齐，会生成 4 条标量读；必须用 `*reinterpret_cast<const float4*>(p)` 才是 1 条 128 位读。改对之后读指令少 4 倍，sector 总数回到理论最小值，时间再快 20%。
- 剩余问题：读 Bs 的 2 路 bank 冲突（4.2M）、写 C 每个请求 32 个 sector、1024³ 的尾部效应。

## 第 8 课：换一种线程→输出的对应方式（v7）

线程 (ty, tx) 仍负责 64 个输出，但行取 ty*4..+3 和 64+ty*4..+3，列取 tx*4..+3 和 64+tx*4..+3（64 = 16 个线程 × 4 = BN/2，保证每格恰好一个线程负责）。

| 指标（1024³） | v6 | v7 |
|---|---|---|
| 时间（1024³ / 2048³） | 0.367 / 2.225 ms | **0.335 / 1.931 ms**（2048³ 为 cuBLAS 的 69.8%） |
| 共享内存 bank 冲突 | 4,194,304 | **0** |
| 共享内存 wavefront | 10.49M | 6.29M（正好少了冲突的 4.19M） |
| 写 C：请求 / 每请求 sector / sector 总数 | 32,768 / 32 / 1.05M | 8,192 / **16** / **131,072**（= 1024² × 4 B / 32 B，理论最小） |
| 寄存器 / 活跃 warp | 127 / 18.7% | 155 / 16.7% |

**结论**：读 Bs 时同一组 8 个线程间隔正好一个 float4，铺满 32 个 bank → 冲突归零；写 C 用 float4 且相邻线程地址连续 → sector 降到理论最小值。寄存器涨到 155，每个 SM 又只能放 1 个 block。

### 实验：`__launch_bounds__(256, 2)`（强制每 SM 至少 2 个 block）

| | v7（默认） | MIN_BLOCKS=2 |
|---|---|---|
| 寄存器 / spill | 155 / 无 | 101 / 无 |
| 活跃 warp（1024³） | 16.7% | 19.3% |
| 总指令数（1024³） | 38.98M | 41.81M（+7%） |
| 时间 1024³ / 2048³ | 0.335 / 1.931 ms | 0.344 / 2.095 ms（**慢 3% / 8%**） |

预测是"快 20–25%"，实测反而变慢。寄存器被压到 101 后，编译器生成的指令多了 7%，并且可同时进行的独立运算变少；
第二个 block 带来的"填空档"收益没有抵消这部分损失。教训：占用率不是越高越好，寄存器换占用率要实测（推断，未做 stall 分解）。

### 实验：BK = 16（每步沿 K 走 16，同步次数减半）

| | BK=8（v7 默认） | BK=16 |
|---|---|---|
| 寄存器 / 共享内存 | 155 / 16 KB | 145 / 32 KB |
| 共享内存读 / FFMA | 0.0625 | 0.0625（每个 kk 仍是 4 条 128 位读、64 次 FFMA） |
| 时间 1024³ / 2048³ | 0.335 / 1.931 ms | 0.328 / 2.171 ms（+2% / −12%） |

结果有好有坏，2048³ 变慢的原因未做进一步分解（笔记本时钟波动约几个百分点，单次测量不足以下结论）。按约定，连续两轮实验都没有超过 5% 的提升 → **FP32 阶段结束，保留 v7（BK=8）**。

## 阶段 A（FP32 CUDA core）总结

| 版本 | 关键改动 | 2048³ 相对 cuBLAS | 1024³ 用时 |
|---|---|---|---|
| v1 naive | 一个线程一个输出，合并访存 | — | 1.71 ms（11.5%） |
| v2 共享内存分块 | block 合作搬运、片上复用 | — | 1.32 ms（14.9%） |
| v3 一维寄存器分块 | 一个 A 在寄存器里用 8 次 | — | 1.14 ms（17.2%） |
| v4 二维寄存器分块 | 8×8 外积，共享内存读 / FFMA 降到 0.06 | 50.9% | 0.535 ms |
| v5 双缓冲 | 预取下一块，消除"等显存" | 51.3% | 0.507 ms |
| v6 float4 + A 转置 | 读指令 ÷4，共享内存读不依赖编译器 | 60.6% | 0.367 ms |
| **v7 线程→输出映射** | bank 冲突归零、写回合并 | **69.8%** | **0.335 ms（58.7%）** |

从 v1 到 v7：1024³ 快 **5.1 倍**；2048³ 达到 cuBLAS SGEMM 的 **69.8%**。
未达到 80% 的已知原因：每 SM 只有 1 个 block（155 个寄存器）、1024³ 的尾部效应、没有做 warp 级分块和按尺寸自动选参数（cuBLAS 会按矩阵大小换 kernel）。

## 第 9 课（补课）：warp 级分块（v8，BM=BN=128，BK=8，warp 64×32，线程 8×8 拆成 2×2 组 4×4，256 线程）

**做法**：用 tid 算 warpId、lane，让 8 个 warp 按 2×4 排，每个 warp 负责 64×32；warp 内 32 个 lane 按 8×4 排。
block 形状（决定显存读多少）和 warp 形状（决定 warp 要从共享内存取多少不同的数）可以分开选。

| 指标（1024³） | v7 | v8 | v8，强制每 SM 1 个 block（`-DEXTRA_SMEM=40960`） |
|---|---|---|---|
| 时间（1024³） | 0.335 ms（58.7%） | **0.278 ms（70.1%）** | 0.299 ms（65.8%） |
| 时间（2048³） | 1.931 ms（69.8%） | **1.869 ms（72.2%）** | 2.059 ms（65.5%） |
| 每个 warp 每个 kk 要的不同的数 | 144 | 96 | 96 |
| 共享内存读指令 | 2,097,152 | 2,097,152 | 2,097,152 |
| 共享内存 wavefront / bank 冲突 | 6.29M / 0 | 6.29M / 0 | 6.29M / 0 |
| 寄存器 / 活跃 warp | 155 / 16.7% | **128 / 19.1%** | 128 / 16.6% |
| 写回 sector / request | 16 | 16 | 16 |

**结论**：
- 每个 warp 要的"不同的数"从 144 降到 96，但共享内存读指令和 wavefront **一个都没少**：这张卡上 LDS.128 的 wavefront 数看起来按指令条数算（平均每条 3 轮），广播多了并没有减少轮数（推断）。教科书说的"减少共享内存流量"在这里没有测出来。
- 主要收益来自**寄存器 155 → 128**：128 × 256 = 32768，每 SM 能放 2 个 block。对照实验把每 SM 限制回 1 个 block，1024³ 慢 7%、2048³ 慢 10%，说明这部分收益确实来自每 SM 2 个 block。1024³ 共 64 个 block、58 个 SM：v7 要两轮（58 + 6），v8 一轮放下。
- 限制成 1 个 block 后，v8 对 v7：1024³ 仍快 11%，2048³ 反而慢 7%，单看 warp 形状没有稳定的收益；剩下的差别未做 stall 分解，笔记本时钟有几个百分点的波动。
- 教训：优化手段的"教科书收益"不一定出现在你的硬件上，真正起作用的可能是它的副作用（这里是寄存器减少），必须做对照实验才能分清。

## 第 10 课：寄存器级双缓冲（v9，片段预取，其余同 v8）

**做法**：regM、regN 各准备两份，按 kk 奇偶轮换；算第 kk 步外积之前先发第 kk+1 步的共享内存读，让读的延迟藏在 64 次 FFMA 后面。

| 指标（1024³，同一时段连续测） | v8 | v9 |
|---|---|---|
| 时间（1024³） | 0.280 ms（70.3%） | 0.284 ms（68.6%） |
| 时间（2048³） | 1.869 ms（72.2%） | 1.878 ms（71.9%） |
| 寄存器 | 128 | 127 |
| 总指令数 | 37,945,856 | 37,945,856（完全相同） |
| 共享内存读指令 / wavefront | 2,097,152 / 6.29M | 2,097,152 / 6.29M |
| stall（每条发射指令平均）：short_scoreboard / mio_throttle / barrier | 0.41 / 0.15 / 0.13 | 0.43 / 0.13 / 0.14 |

**结论**：没有变化（差别在测量波动内）。kk 循环是 `#pragma unroll` 完全展开的，编译器在 v8 里就已经自己把下一步的 LDS 提前、和 FFMA 交错排好了（总指令数一条不差、寄存器几乎一样，推断生成的 SASS 基本相同，未逐条比对）。
手写寄存器双缓冲在循环**不展开**（或编译器排不过来）的时候才有用；CUTLASS 等库仍然显式写出来，是为了不依赖编译器。

## 第 11 课：AsT 每行加 padding，消除转置写入的 2 路冲突（v10，APAD=4，其余同 v9）

**问题**：搬 A 时 lane 0、lane 1 的 aRow 相同，aCol 为 0 和 4，写 `AsT[aCol+j][aRow]` 的地址差 4 × 128 = 512，512 % 32 = 0 → 同一 bank，每条 STS.32 两轮。
**做法**：每行长度改为 128 + APAD。地址差 = 512 + 4·APAD，要求 4·APAD % 32 ≠ 0（最好 = 16，两组 16 个 lane 正好错开 16 个 bank），且 APAD 是 4 的倍数（每行起点 16 字节对齐，才能 float4 读）→ **APAD = 4**。
（APAD = 16 时 4·16 = 64 仍是 32 的倍数，冲突不变，实测 262,144 次冲突，作为反例保留。）

| 指标 | v9 | v10（APAD=16，反例） | v10（APAD=4） |
|---|---|---|---|
| 共享内存写冲突 | 262,144 | 262,144 | **0** |
| 共享内存写 wavefront | 786,432 | 786,432 | **524,288** |
| 共享内存读冲突 / wavefront | 0 / 6.29M | 0 / 6.29M | 0 / 6.29M |
| 共享内存用量 | 16,384 B | 17,408 B | 16,640 B |
| short_scoreboard stall | 0.43 | 0.23 | 0.23 |
| 1024³ | 0.284 ms | 0.281 ms | 0.281 ms |
| 2048³（v9、v10 交替各跑两次） | 1.866 / 1.959 ms | — | 1.853 / 1.872 ms |

**结论**：冲突按预期清零，写 wavefront 少 262,144 轮。但这只占共享内存总轮数（≈ 7.08M）的 3.7%，时间上测不出来：同一个程序两次运行就能差 5%（笔记本时钟），v9 / v10 的差别在波动以内。
short_scoreboard 降了近一半时间却没变：stall 是"某个 warp 在等"，只要调度器还能从别的 warp 里挑出可发射的指令，SM 就没有闲着（推断）。
按约定，v9、v10 连续两轮提升都 < 5%。

## 测量方法修正：交替计时（机器 B，CUDA 12.4）

**发现**：4096³ 时我们的 kernel 达到 cuBLAS 的 100%，而 cuBLAS 自己比 2048³ 还慢，看起来不对劲。逐步排查：
1. `nvidia-smi` 采样：时钟 1395 MHz，无降频标志 → 一开始否定了"功耗墙"（采样太稀，后来证明没抓到）。
2. ncu 单次启动：4096³ 时 cuBLAS（`cutlass_80_simt_sgemm_128x64_8x5_nn_align1`，CUTLASS SIMT、5 级 cp.async 流水）约 9.0 ms，我们 9.04 ms；正式计时却都是 14.3 ms。
3. `WARMUP=0 REPS=1` 只测一次：2048³ 我们 1.365 ms、cuBLAS 1.363 ms（99.8%），而顺序计时下我们是 1.86 ms（73%）。
4. `SHOW_REPS=1` 打印每次耗时 + `ME_FIRST=1` 交换顺序：**先测的一方一直稳定，后测的一方从第 3 次左右起从 1.35 ms 跳到 1.7–1.9 ms，跟是谁无关。**

| 2048³，顺序计时 | 先测的一方（每次耗时） | 后测的一方（每次耗时） |
|---|---|---|
| 默认（先 cuBLAS） | cuBLAS：1.347–1.350 ms | v10：1.365, 1.367, 1.482, 1.945 … 1.802 |
| ME_FIRST=1（先 v10） | v10：1.362–1.368 ms | cuBLAS：1.349, 1.586, 1.698 … 1.849 |

**修正**：`common.cuh` 默认改为交替计时（cuBLAS、kernel 轮流各跑一次，两边经历同样的降频过程）；`SEQUENTIAL=1` 可切回旧方式。

**修正后的结果**（交替计时，3 次热身 + 20 次，中位数；毫秒数随降频状态变化，主要看百分比）：

| 版本 | 1024³ | 2048³ | 4096³ |
|---|---|---|---|
| v7 线程→输出映射 | 0.332 ms，58.6% | 81.4% | 78.2% |
| **v8 warp 级分块** | **0.278 ms，70.1%** | **98.9%** | **94.2%** |
| v10（v8 + 寄存器预取 + AsT padding） | 0.278 ms，70.1% | 98.3% | 94.5% |

**结论**：
- 2048³ 达到 cuBLAS SGEMM 的约 **98–99%**，4096³ 约 **94%**，超过 80% 的目标，FP32 阶段完成。
- v7 → v8（warp 级分块）在 2048³ 上是 81% → 99%，比顺序计时下看到的 70% → 72% 大得多：之前的提升被降频掩盖了。
- 1024³ 仍是 70%：只有 64 个 block、58 个 SM，cuBLAS 会针对小尺寸换 kernel（2048³ 用 `ampere_sgemm_128x64_nn`），我们只有一套固定分块。
- v9（寄存器预取）、v10（AsT padding）在公平计时下依然测不出差别，和之前的结论一致。
- 教训：**计时方法本身也要验证**。"后测的那个吃亏"这类系统误差，重复多少次都不会消失，只有交换顺序、看每次耗时才能发现。

# 阶段 B：张量核心（FP16 输入，FP32 累加；参照 cuBLAS GemmEx；交替计时）

## 第 12 课：最朴素的 WMMA（tc01）

**做法**：每个 warp 负责 C 的一个 16×16，沿 K 每次 16，直接从显存 `load_matrix_sync` 读 A、B 的 16×16 片段，`mma_sync` 累加，不用共享内存。block = 4 个 warp（2×2）。

| | 2048³ | 4096³ |
|---|---|---|
| cuBLAS SGEMM（FP32，CUDA core） | 1.396 ms，12.3 TFLOPS | 11.97 ms，11.5 TFLOPS |
| cuBLAS GemmEx（FP16，张量核心） | 0.547 ms，**31.4 TFLOPS（2.55× SGEMM）** | 4.575 ms，**30.0 TFLOPS（2.62×）** |
| tc01 朴素 WMMA | 1.884 ms，9.1 TFLOPS（29.0% of GemmEx） | 18.49 ms，7.4 TFLOPS（24.7%） |

**分析**：
- 张量核心本身：GemmEx 是 SGEMM 的 2.6 倍（白皮书推算的计算峰值比是 2 倍；SGEMM 只跑到 FP32 峰值的约 55–60%，GemmEx 跑得更满）。
- 朴素 WMMA 比我们最好的 FP32 kernel（v8）还慢：每个 warp 每步从显存（经 L2）读 16×16 的 A 和 B（共 1 KB），只做 4096 次乘加，每个读进来的数只用 16 次。
  4096³ 总共要读 (4096/16)³ × 1 KB = **16 GB**；v8 的 block 是 128×128，每个数在共享内存里被用 128 次，总共只读约 4 GB。
  算得快了 2.6 倍，但要搬的数据多了 4 倍 → 卡在数据搬运上，张量核心大部分时间在等。
- 下一步和阶段 A 一样：共享内存分块（block 合作搬运、片上复用），再让每个 warp 算多个 16×16 片段（寄存器层面的复用）。
