# matmul 结果记录

> **硬件与软件**：机器 B，HP OMEN 17 笔记本，RTX 3080 Ti Laptop GPU（Ampere，sm_86，58 SM，4 MB L2），CUDA 12.4，Nsight Compute（`--clock-control none`）。
> 笔记本 GPU 的时钟随负载变化：重负载时约 1.4 GHz，对应 FP32 峰值约 21 TFLOPS；标称 31.2 TFLOPS 对应 2.1 GHz。
> 所以不同运行之间直接比毫秒不完全可靠，**主要看"相对 cuBLAS 的百分比"**。

## 总览（M = N = K = 1024，FP32）

| 版本 | 做了什么 | 时间 | TFLOPS | 相对 cuBLAS |
|---|---|---|---|---|
| cuBLAS SGEMM | 参照 | 0.195 ms | 11.0 | 100% |
| v1 naive，x→行（反面教材） | 一个线程算一个输出；相邻线程算相邻的**行** | 13.9 ms | 0.15 | 1.4% |
| v1 naive，x→列，块 8×32 | 相邻线程算相邻的列，但一个 warp 跨 4 行 | 2.13 ms | 1.01 | 9.1% |
| v1 naive，x→列，块 32×8 | 相邻线程算相邻的**列**（合并访存） | 1.71 ms | 1.26 | 11.5% |
| **v2 共享内存分块（TILE=32）** | block 合作把 A、B 小块搬进共享内存，再在片上复用 | **1.43 ms** | **1.50** | **13.6%** |

## 第 1–2 课：naive 与合并访存

**做法**：保持计算不变，只改"线程 → 输出元素"的映射和线程块形状，用 Nsight Compute 量 L1 的访存模式。

| 指标（ncu） | x→列 32×8 | x→列 8×32 | x→行 32×8 |
|---|---|---|---|
| 全局读 request 数 | 67.1M | 67.1M | 67.1M |
| 每个 request 的 sector 数 | 2.5 | 2.5 | 16.5 |
| 每个 request 碰到的 cache line 数（手算） | 1 | 2.5 | 16.5 |
| L1 命中率 | 87.5% | 87.7% | 98.0% |
| DRAM 吞吐（占峰值） | 10.6% | 6.8% | 2.7% |
| L1/TEX 吞吐（占峰值） | 98.4% | 97.6% | 97.9% |

**结论**
- **合并访存**：x→行时一个 warp 的 32 个线程读 A 的 32 个不同行，每次读要碰 32 个 sector；x→列时是 1 个。实测 sector 总数相差 6.6 倍，与手算的 33 : 5 一致，时间相差约 8 倍。
- **复用体现在命中率，不体现在 sector 数**：87.5% = 1/8 miss。A 的一个 sector 供同一 warp 的连续 8 次 k 循环使用；B 的一个 sector 被同一 block 的 8 个 warp 共用。
- **sector 数相同，cache line 数也要看**：8×32 的块和 32×8 的 sector 数一样，但读 A 时一次碰 4 条不同的 line，慢了约 25%。按数据反推，这两种慢的配置都接近"每 SM 每周期处理约 1 条 line"（待用 ncu 指标直接验证）。
- **瓶颈**：不是 DRAM（约 10%），也不是算力（FFMA 只占指令的 21%，约用到 FMA 峰值的 6%）；是 **L1/TEX 被读请求占满**。每做 1 条 FFMA 就要 2 条全局读，这是下一课 tiling 要解决的问题。

## 第 3 课：共享内存分块（v2，TILE = 32）

**做法**：一个 32×32 的 block 负责 C 的一个 32×32 小块；沿 K 每步由每个线程搬 1 个 A、1 个 B 进共享内存，`__syncthreads()` 后在共享内存里做 32 次乘加，再同步。

| 指标（ncu，1024³） | v1（x→列 32×8） | v2 |
|---|---|---|
| 时间 | 1.71 ms | 1.43 ms |
| 全局读 request | 67.1M | **2.1M**（少 32 倍 = TILE） |
| 每条 FFMA 配的全局读 | 2 | **0.0625** |
| 每条 FFMA 配的共享内存读 | 0 | **1.25**（源码是 2；编译器把 As 一行连续 4 个数合成一条 128 位读） |
| 共享内存 bank 冲突 | — | 0 |
| L1 命中率 / L2 命中率 | 87.5% / 87.4% | 0% / 70.9%（复用已搬进共享内存；不同 block 读同一小块靠 L2） |
| L1/TEX 吞吐 | 98.4% | 79.9% |
| 活跃 warp（占用率） | 96.7% | 66.6%（1024 线程的 block，每 SM 只放得下 1 个） |

**结论**
- 全局读按预期减少到 1/TILE，但时间只快了约 1.2 倍。
- 原因：共享内存读也走 SM 里同一个 L1/TEX 单元。每条 FFMA 仍要配 1.25 条共享内存读，访存指令只从 2 条/FFMA 降到约 1.3 条/FFMA；再加上每步两次全 block 同步、每 SM 只有 1 个 block，同步时没有别的 block 填空档（后两点待用 stall reason 验证）。
- 下一步（寄存器分块）：让每个线程算多个输出，把读进寄存器的数复用多次，降低"共享内存读 / FFMA"。
